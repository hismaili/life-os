# 01 — Specification: Create Projects Database

Status: Draft for Architect review
Owner (Specifier stage): pipeline automation
Source input: feature request "Create Projects Database" + `CLAUDE.md`; `docs/architecture/03-Domain-Model.md`; `docs/architecture/04-Bounded-Contexts.md` (use-case catalogue); `docs/architecture/05-Ubiquitous-Language.md` (present but **empty** in-repo — no content to cite); `docs/productivity/PARA.md` and `docs/productivity/GTD.md` (present but **empty** in-repo — no content to cite; see §7 for how this gap is handled); the completed **Create Dashboard** pipeline (`docs/pipeline/create-dashboard/01-spec.md`, `02-architecture.md`); and existing code under `backend/src/main/java/com/lifeos/{domain/{project,workspace},application/{usecase/project,usecase/workspace,port,dto/workspace},infrastructure/adapter/notion}`.

> This spec covers **one Phase-B provisioning step**: the creation/verification/repair of the **Projects** database as a child of the already-provisioned Dashboard page. It is the **first of the seven Phase-B database steps** (Projects, Tasks, Knowledge, Habits, Journal, Resources, People — `CreateWorkspaceService.java` lines 30–36, 54–61) and therefore sets the reusable pattern the other six will mirror. It does **not** re-specify the orchestrator (`CreateWorkspaceUseCase`), the Dashboard step, the other six database steps, relations/rollups/formulas, or sample data — those are separate, already-specified-or-future collaborators. Where this spec repeats a decision already made by Create Dashboard's architecture (strict idempotency, verify-before-trust, per-step ledger transaction, single process-level token, fail-loudly on `>1` identity match), it does so only to bind this step to that contract, not to re-litigate it.

## 1. Summary

"Create Projects Database" is a Phase-B provisioning step invoked by the Create Workspace orchestrator once Phase A (Create Dashboard) succeeds: given an existing `Workspace` aggregate and its confirmed Dashboard page id, it provisions (or, on re-run, verifies and reconciles) a single Notion database — **Projects** — as a child of the Dashboard, with the structural property schema needed to represent the `Project` aggregate. The user value: every workspace gets one stable, non-duplicated Projects database, created once, whose schema is verified and repaired on every re-run rather than drifting silently — the foundation Task, Goal, and Area relations (added later, by the Create Relations phase) will attach to. Today `CreateProjectsDatabaseService` throws `UnsupportedOperationException` and the database slice of `NotionProvisioningAdapter` (`createDatabase`, `verify`, `findChildByIdentity`, `repairShape`) is unimplemented; this spec defines what "implemented" must mean for this step specifically, and — because it is first — for the six sibling database steps that will reuse its pattern.

## 2. Actors & stakeholders

- **Primary user (Person aggregate)** — indirectly benefits; does not invoke this step directly. Invokes "Create Workspace," which invokes this step as part of Phase B.
- **`CreateWorkspaceUseCase` / `CreateWorkspaceService` (orchestrator)** — the sole caller of `CreateProjectsDatabaseUseCase.execute(workspaceId)`, already wired (`CreateWorkspaceService.java` line 30, 54). Runs this step only if Phase A (Dashboard) succeeded (`runOrBlock(phaseAOk, …)`); treats this step's `ProvisioningStepResult` as one of seven inputs to `phaseBOk`, which gates Phase C (Relations).
- **`CreateProjectsDatabaseService` (this step's application service)** — currently a stub (`CreateProjectsDatabaseService.java`); owns the step's idempotent verify/create/repair/adopt/record sequence for the `PROJECTS_DB` resource. Depends on `NotionProvisioningPort` and `WorkspaceLedgerWriter`.
- **`NotionProvisioningPort` / `NotionProvisioningAdapter` (infrastructure)** — driven port/adapter; its database-oriented members (`createDatabase(rootPageId, DatabaseSpec)`, `verify(rootPageId, type, ExpectedShape)`, `findChildByIdentity(rootPageId, type)`, `repairShape(notionId, ExpectedShape)`) are today `UnsupportedOperationException` and must become real for the Projects resource in this branch. Making them real for the *other six* database types is out of scope here but will reuse the same method signatures.
- **`WorkspaceLedgerWriter`** — the shared, already-implemented collaborator (`record(workspaceId, PROJECTS_DB, notionId)`) that performs this step's ledger write in its own `@Transactional` unit. This spec does not change its contract.
- **Downstream pipeline roles (Architect, SME, Implementer, QA, Auditor)** — consumers of this spec, and — because this is the pattern-setting first database step — implicit consumers of whatever generalizable design falls out of it for the remaining six.

## 3. Functional requirements

- **FR-1**: The system shall accept a request to provision the Projects database for an existing `Workspace`, identified by `workspaceId` (`UUID`), matching the existing `CreateProjectsDatabaseUseCase.execute(UUID workspaceId)` contract (`CreateProjectsDatabaseUseCase.java`). No other input is required — the database's title, parent page, and property schema are derived from the `Workspace` aggregate and this step's own fixed schema definition (§3, property table), not supplied by the caller.
- **FR-2**: Given a `workspaceId` that does not correspond to any persisted `Workspace`, the system shall fail explicitly (not silently no-op), surfacing an error the orchestrator converts into a `FAILED` `ProvisioningStepResult` (mirrors Create Dashboard FR-2 and `WorkspaceLedgerWriter`'s existing "Workspace not found" convention).
- **FR-3**: Given a `workspaceId` whose `Workspace` has no confirmed `DASHBOARD` ledger entry, the system shall fail explicitly rather than attempt to create a database with no known parent page — this step's precondition is a live, verified Dashboard id (in practice already enforced by the orchestrator's `runOrBlock(phaseAOk, …)`, `CreateWorkspaceService.java` line 54, but this step must not silently proceed if invoked directly with that precondition unmet).
- **FR-4**: On a valid request where the Workspace's provisioning ledger has **no** `PROJECTS_DB` entry, and live verification against Notion (scoped to children of the confirmed Dashboard page) finds no matching database, the system shall create exactly one new Notion database as a child of the Dashboard page, titled with a deterministic identity marker `[ASSUMPTION — exact title string, e.g. "Projects"; template is an Architect/SME decision, not fixed here, mirroring Create Dashboard FR-3's title-template deferral]`, with the property schema defined in §3's property table, and record it in the ledger with its Notion database id. Outcome: `CREATED`.
- **FR-5**: On a valid request where the ledger has a `PROJECTS_DB` entry **and** live verification confirms the referenced Notion database still exists and matches the expected shape (title + the full required-property set of §3), the system shall make no write calls to Notion and shall report outcome `RECONCILED`.
- **FR-6**: On a valid request where the ledger has a `PROJECTS_DB` entry but live verification finds the referenced Notion database **missing** (deleted out-of-band) or **present but drifted** (renamed, or missing one or more required properties from §3), the system shall repair it — re-creating the database if deleted, or correcting the drifted shape (renaming and/or adding the missing properties) if present-but-wrong — and shall update the ledger entry with the (possibly new) Notion database id. Outcome: `REPAIRED`.
- **FR-7**: Before trusting any ledger-recorded Projects-database id, the system shall verify it live against Notion (existence + expected shape) rather than assuming the ledger is accurate — the ledger is a hint, live Notion is the source of truth (mirrors Create Dashboard FR-6; inherits Create Workspace's strict-idempotency contract).
- **FR-8**: If no ledger entry exists but a database matching the expected Projects-database identity (deterministic identity: a database directly parented under the confirmed Dashboard page carrying the expected title marker) is found live in Notion, the system shall adopt that database's id into the ledger rather than creating a duplicate — closing the create-succeeded-but-ledger-write-failed race window (mirrors Create Dashboard FR-7; uses `NotionProvisioningPort.findChildByIdentity(rootPageId, PROJECTS_DB)`).
- **FR-9**: Where identity resolution (FR-8, or the drift check in FR-6) finds **more than one** database under the Dashboard matching the Projects identity, the system shall fail loudly (not adopt or repair an arbitrary match) — mirrors Create Dashboard's `>1` match → `FAILED` rule (`docs/pipeline/create-dashboard/02-architecture.md` §4.1/§4.2).
- **FR-10**: The system shall record the confirmed Notion database id (whether newly created, reconciled, or repaired) into the Workspace provisioning ledger via the existing `WorkspaceLedgerWriter.record(workspaceId, PROJECTS_DB, notionId)` collaborator, in that collaborator's own short transaction — this step does not introduce a new transactional write path.
- **FR-11**: The system shall return a `ProvisioningStepResult(PROJECTS_DB, outcome, detail)` reflecting exactly one of `CREATED`, `RECONCILED`, `REPAIRED`, or a propagated failure for every invocation — never `void`, never a swallowed exception (matches the existing interface signature, `ProvisioningStepResult`'s compact-constructor contract, and `CLAUDE.md` "no silent no-op").
- **FR-12**: When Notion API calls made by this step fail (network error, rate limit, authentication/token failure, unexpected response shape), the system shall not partially update the ledger — either the full verify-and-write sequence for this step succeeds and the ledger reflects the confirmed state, or it fails and the ledger is left exactly as it was before this invocation. The failure shall propagate as an exception for the orchestrator to convert to a `FAILED` result (FR-11), not be swallowed inside this step.
- **FR-13**: Re-running this step any number of times for the same `workspaceId` with no out-of-band changes to Notion shall converge to the same single Projects database (same Notion id) and never create a second database — the idempotency contract this spec exists to bind (`CLAUDE.md`; Create Dashboard FR-11).
- **FR-14**: This step shall create/verify/repair **only** the Projects database's own structural shape (title + the property schema of §3) — it shall not create, populate, or verify any relation, rollup, formula, database row, or sample record, and it shall not touch any other provisioned resource (`DASHBOARD`, other `*_DB` types). Cross-database relation properties (e.g. a Notion "relation" property pointing at the Tasks, Goals, or Areas database) are explicitly excluded from this step's created shape — see §8.

Establishing such relations, if and when the target databases exist, belongs to the "Create Relations" phase, not this step (§8; open question in §9).

## 4. Acceptance criteria (Given/When/Then)

**FR-1 — input contract**
- Given a valid `workspaceId` for an existing `Workspace` with a confirmed Dashboard, when `CreateProjectsDatabaseUseCase.execute(workspaceId)` is called, then the step runs without requiring any additional caller-supplied parameter.

**FR-2 — workspace not found**
- Given a `workspaceId` with no corresponding persisted `Workspace`, when the step executes, then it throws (e.g. `IllegalStateException`, matching `WorkspaceLedgerWriter`'s existing convention) and makes no Notion API call.

**FR-3 — missing Dashboard precondition**
- Given a `Workspace` whose ledger has no confirmed `DASHBOARD` entry, when the step executes, then it fails explicitly (throws, or is never reached because the orchestrator's `runOrBlock` already returned `BLOCKED`) rather than attempting a Notion call with an unknown parent page id.

**FR-4 — first-time creation**
- Given a `Workspace` whose ledger has no `PROJECTS_DB` entry and Notion has no matching database under the confirmed Dashboard, when the step executes, then exactly one new Notion database is created as a child of the Dashboard with the full property schema of §3, the ledger gains a `PROJECTS_DB` entry with that database's id, and the returned `ProvisioningStepResult` has `outcome = CREATED`.

**FR-5 — pure reconcile (idempotent re-run, no drift)**
- Given a `Workspace` whose ledger has a `PROJECTS_DB` entry and live Notion verification confirms that database exists with the expected title and the full required-property set, when the step executes, then no Notion write call is made, the ledger is left unchanged, and the returned result has `outcome = RECONCILED`.

**FR-6a — repair after out-of-band deletion**
- Given a `Workspace` whose ledger has a `PROJECTS_DB` entry but the referenced Notion database no longer exists, when the step executes, then a new Projects database is created (or, per FR-8, an orphan matching identity is adopted first), the ledger's `PROJECTS_DB` entry is updated to the resulting id, and the returned result has `outcome = REPAIRED`.

**FR-6b — repair after out-of-band drift (rename or missing property)**
- Given a `Workspace` whose ledger has a `PROJECTS_DB` entry and the referenced Notion database still exists but has been renamed or is missing one or more required properties from §3, when the step executes, then the database's shape is corrected in place (same Notion id retained; missing properties added, title corrected), the ledger entry is confirmed/updated, and the returned result has `outcome = REPAIRED`.

**FR-7 — verify-before-trust**
- Given a `Workspace` whose ledger has a `PROJECTS_DB` entry, when the step executes, then it calls Notion to verify that entry's live existence and full property shape before returning `RECONCILED` — it never returns `RECONCILED` purely because a ledger row is present.

**FR-8 — orphan adoption (race recovery)**
- Given a `Workspace` whose ledger has no `PROJECTS_DB` entry, but a database matching the expected Projects identity already exists live in Notion as a child of the Dashboard (e.g. a prior run created it but crashed before the ledger write), when the step executes, then the existing database is adopted (its id recorded in the ledger) rather than a second database being created, and the returned result reflects `RECONCILED` (if matching) or `REPAIRED` (if drifted) — never `CREATED`, since no new database was made.

**FR-9 — fail loudly on ambiguous identity**
- Given more than one database under the Dashboard matches the expected Projects identity (title marker), when the step executes its identity lookup, then it does not adopt or repair any of them; it fails, and the returned/propagated result is `FAILED` with a non-blank `detail` explaining the ambiguity.

**FR-10 — ledger write path**
- Given any of the FR-4/FR-5/FR-6/FR-8 scenarios reach a confirmed Notion database id, when the step completes, then the ledger update is performed through `WorkspaceLedgerWriter.record(workspaceId, PROJECTS_DB, notionId)` and that write is durably committed in its own transaction, independent of the orchestrator's transaction boundary.

**FR-11 — result contract**
- Given any successful execution path, when the step returns, then the result's `type` is `PROJECTS_DB` and `outcome` is exactly one of `CREATED`/`RECONCILED`/`REPAIRED`.
- Given any failure path, when the step raises an exception, then no `ProvisioningStepResult` is fabricated by this step itself — the exception propagates for the orchestrator's `runOrBlock`/`runStep` to convert into `FAILED` with a non-blank `detail`.

**FR-12 — no partial ledger write on external failure**
- Given a Notion API call within this step fails (timeout, 5xx, rate limit, 401/403), when the step executes, then the ledger is not modified, and the thrown exception surfaces to the caller unmodified in essence.
- Given the Notion API call succeeds but the subsequent `WorkspaceLedgerWriter.record` call fails, when the step executes, then the created/repaired Notion database is left in place (Notion has no transactional rollback), and the next run's FR-8 orphan-adoption path is responsible for reconciling the ledger to the already-existing database.

**FR-13 — idempotent convergence**
- Given the step is run three times consecutively with the same `workspaceId` and no out-of-band Notion changes between runs, when each run completes, then exactly one Projects database exists in Notion across all three runs, and the ledger's `PROJECTS_DB` entry references that same database id after every run.

**FR-14 — scope boundary**
- Given the step completes successfully, when its `NotionProvisioningPort` call log/interactions are inspected, then no `ensureRelation`, `ensureRollup`, `ensureFormula`, `insertSampleRecords`, or any other database type's `createDatabase`/`verify`/`repairShape` call is invoked by this step.
- Given the created or verified Projects database's schema is inspected, when compared against §3's property table, then it contains no relation-typed property pointing at another LifeOS database.

## 5. Non-functional requirements

- **NFR-1 (Strict idempotency)**: This step must be safely re-runnable any number of times per FR-13, consulting live Notion (not just the ledger) as the source of truth — inherits Create Dashboard's idempotency contract; this spec does not weaken it for the Projects database specifically.
- **NFR-2 (Resilience to external failures)**: A Notion API failure during this step must leave both the ledger and any already-created Notion database in a state the *next* run can reconcile without manual cleanup (FR-12); no compensating transaction/rollback of the Notion side is required or expected.
- **NFR-3 (Testability)**: `CreateProjectsDatabaseService`'s verify/create/repair/adopt/record sequencing logic must be unit-testable against a mocked `NotionProvisioningPort` and `WorkspaceLedgerWriter`, with zero real Notion calls.
- **NFR-4 (No silent no-op)**: Until the Notion adapter's relevant database methods (`createDatabase`, `verify`, `findChildByIdentity`, `repairShape`) are genuinely implemented for the Projects resource, `CreateProjectsDatabaseService.execute` must continue to fail explicitly (`UnsupportedOperationException` or equivalent) rather than appear to succeed.
- **NFR-5 (Observability)**: Each invocation's outcome (`CREATED`/`RECONCILED`/`REPAIRED`/failure) must be logged with enough detail (workspaceId, Notion database id, prior ledger state) to debug a multi-run reconciliation history — feeds the orchestrator's `ProvisioningReport`.
- **NFR-6 (Security / no token leakage)**: This step uses the single process-level Notion integration token already decided for v0; it introduces no new secret or token-scoping requirement. The token must never appear in logs or the `detail` field of a `ProvisioningStepResult` or in any propagated exception message.
- **NFR-7 (Failure isolation)**: A failure in this step (FR-11/FR-12) must not corrupt or partially mutate any other provisioned resource's ledger entry (`DASHBOARD` or any other `*_DB` type) — the orchestrator's existing `runOrBlock` per-step isolation (`CreateWorkspaceService.java` lines 54–61, each `dbResults` entry independently computed) already provides this at the orchestration level; this step must not introduce any shared mutable state or side effect that breaks that isolation (e.g. it must not write to another resource's ledger entry, and one database step's failure must leave the sibling database steps free to still run per the orchestrator's existing `phaseBOk` aggregation, which only gates Phase C, not the sibling Phase-B steps themselves).
- **NFR-8 (Ledger recording)**: Every successful terminal outcome (`CREATED`/`RECONCILED`/`REPAIRED`) must result in exactly one `PROVISIONED_RESOURCE` ledger entry of type `PROJECTS_DB` reflecting the confirmed Notion id — never zero (a successful-looking result with no ledger record) and never more than one (a duplicate/stale entry for the same type), consistent with `Workspace.record`'s upsert-by-type semantics (`Workspace.java` lines 60–68).
- **NFR-9 (Performance)**: `[ASSUMPTION]` No hard latency SLA; a single successful run should require at most a small, bounded number of Notion API calls (one verify/search + at most one create-or-repair + one ledger write) — no polling loops or unbounded retries within a single invocation (mirrors Create Dashboard NFR-7).
- **NFR-10 (Rate-limit awareness)**: `[ASSUMPTION — carried from Create Dashboard NFR-8]` Notion's documented rate limit applies; this step's implementation must not assume unlimited throughput, though the specific backoff strategy is an Architect/Implementer decision, not fixed here.

## 6. Data & entities (conceptual only)

- **Workspace**: existing aggregate root that owns the provisioning ledger this step reads from and writes to, and whose confirmed `DASHBOARD` ledger entry supplies this step's required parent-page id. Referenced here only by its `id` (UUID).
- **Project**: existing domain aggregate (`domain/project/Project.java`) this database represents — `name`, `description`, `areaId`, `workspaceId`, `goalId`. This step provisions the *structural container* (database + property schema) for future `Project` records; it does not create any row/record.
- **Projects database**: the single Notion database that is this step's sole subject — a database directly parented under the workspace's Dashboard page, with the property schema of §3. Conceptually: `Workspace 1—0..1 ProjectsDatabase` before this step runs, `Workspace 1—1 ProjectsDatabase` after a successful run.
- **Provisioned Resource (type = PROJECTS_DB)**: the existing ledger entry value object (`ProvisionedResourceType.PROJECTS_DB`, `notionId`, `provisionedAt`) this step is responsible for creating/updating. No new domain type is introduced by this spec.
- **Expected Shape (Projects)**: the conceptual target state this step verifies against — title + the required-property-name set of §3 (`ExpectedShape(String title, List<String> requiredPropertyNames)`, `application/port/ExpectedShape.java`).

Relationships: `Project.areaId` and `Project.goalId` describe conceptual links to the `Area` and `Goal` aggregates, but establishing the corresponding Notion relation properties is explicitly not this step's concern (§8) — those aggregates' representation in Notion (if any) is a separate, currently-undecided matter (§9).

## 7. Constraints & assumptions

- Constraint: must implement the existing `CreateProjectsDatabaseUseCase.execute(UUID workspaceId) : ProvisioningStepResult` signature and the existing `CreateProjectsDatabaseService` class (currently a stub) without changing the interface shape — the orchestrator (`CreateWorkspaceService`) already depends on this exact contract.
- Constraint: must use the existing `WorkspaceLedgerWriter.record(...)` collaborator for the ledger write; this spec does not reopen the transaction-boundary decision made for Create Dashboard.
- Constraint: must use the existing `NotionProvisioningPort` database-oriented contract (`createDatabase(String rootPageId, DatabaseSpec)`, `verify(String rootPageId, ProvisionedResourceType type, ExpectedShape)`, `findChildByIdentity(String rootPageId, ProvisionedResourceType type)`, `repairShape(String notionId, ExpectedShape)`) as already defined in `application/port/`. If this step's needs cannot be met by the existing port shape, that is an Architect-level finding, not a redesign this spec pre-decides.
- `[ASSUMPTION — carried from repo state]` `docs/productivity/PARA.md` and `docs/productivity/GTD.md` exist as files but contain no text in this repository as of this spec's writing. Property-set claims attributed to "PARA" in §3 are grounded in an external, publicly published summary of the PARA method (Tiago Forte, fortelabs.com/blog/para/, retrieved via web search for this spec), not in the repo's own (currently empty) productivity docs. This is flagged so the Architect/SME can either (a) populate the repo's productivity docs with the actual source material so future specs can cite them in-repo, or (b) confirm the external citation is an acceptable substitute for this branch.
- `[ASSUMPTION]` The Projects database's identity for verification/adoption purposes (FR-8) is "a database directly parented under the confirmed Dashboard page carrying the deterministic title marker" — mirrors Create Dashboard's heuristic identity approach (title + parent scoping), adapted from a root page (no parent) to a child database (parent = Dashboard, so scoping is simpler and unambiguous by construction, modulo Notion allowing duplicate titles under the same parent, hence FR-9).
- `[ASSUMPTION]` Database title format/content beyond "identifies the Projects resource" (FR-4) is not fixed by this spec; downstream stages choose it (e.g. "Projects").
- `[ASSUMPTION]` "Status" and "Due Date" as required properties (§3) are the one part of this spec not directly traceable to the `Project` domain entity as it exists in code today. This is a deliberate, flagged gap — see open question §9(1) — not an attempt to redefine the domain model unilaterally.
- Constraint: single process-level Notion token (no per-Person token) — inherited unchanged from Create Workspace/Create Dashboard.

## 8. Out of scope

- Establishing any Notion relation, rollup, or formula property, including but not limited to a Projects↔Tasks, Projects↔Goals, or Projects↔Areas relation — that is the "Create Relations" phase (Phase C), specified separately.
- Any database property whose Notion type requires another LifeOS-provisioned database to exist first (relation-typed properties in general).
- The Areas and Goals aggregates' own database provisioning — neither is among the seven Phase-B steps this pipeline branch (or its five siblings under active specification) implements; whether/when an Areas or Goals database is ever created is undecided (open question §9).
- Populating the Projects database with rows or sample data — that is the "Populate Example Data" phase (Phase F), out of scope here.
- Provisioning any of the other six databases (Tasks, Knowledge, Habits, Journal, Resources, People) — each gets its own spec; this document only defines the contract for the Projects step, even though its pattern is expected to generalize.
- The orchestrator's (`CreateWorkspaceService`) sequencing, blocking, and reporting logic — already implemented; this spec only defines the contract this one step must fulfill within that sequence.
- The Create Dashboard step itself, and any change to how the Dashboard's id is confirmed — this step only consumes that confirmed id as a precondition (FR-3).
- Real OAuth / interactive Notion authorization flow — unchanged from Create Dashboard/Create Workspace's single pre-provisioned process-level integration token.
- Database view configuration (Notion "views" — board/table/calendar/filters/sorts), icon/cover, or any presentation concern beyond the property schema needed to identify and later relate to this database — a presentation concern for `notion/` assets (per `CLAUDE.md`), not this backend provisioning step.
- Projects database deletion or archival.
- Any change to `NotionProvisioningPort`'s method signatures or value types — if the Architect determines the existing database-oriented port shape is insufficient, that is a finding to raise, not something this spec pre-decides.
- Extending the `Project` domain entity itself (e.g. adding `status`/`dueDate` fields) — whether/how the domain model changes to back the Notion-side Status/Due Date properties of §3 is an Architect/SME decision, flagged as an open question (§9), not decided or implemented by this spec.

## 9. Open questions for the stakeholder

1. `Project.java` currently has no `status` or `dueDate` field, but §3 requires the created Notion database to carry `Status` and `Due Date` properties (grounded in the PARA method's external definition of "project," not in the domain model or in this repo's own — currently empty — `docs/productivity/PARA.md`/`GTD.md`). Should the `Project` domain aggregate be extended with these fields so the Notion view has a backing source of truth, or should these remain Notion-only presentation properties with no domain-model backing for v0? This materially affects whether "Create Projects Database" alone is sufficient, or whether a domain-model change must land first.
2. Is there a plan for an **Areas** database at all? It appears in `domain/project/Project.java` (`areaId`) and in the aggregate catalogue (`docs/architecture/03-Domain-Model.md`), but it is absent from every provisioning use-case list found in the docs (`docs/architecture/04-Bounded-Contexts.md` lists Projects, Tasks, Knowledge, Habits, Journal, Resources, People, and separately Goals/Reviews — never Areas). Without an Areas database, `Project.areaId` can never surface as a Notion relation. Should this spec's sibling database steps include one, or is "Area" meant to be represented a different way in Notion (e.g. a Select property with a fixed value list instead of a relation)?
3. Is a **Goals** database committed for this pipeline's near-term roadmap (it's listed in `docs/architecture/04-Bounded-Contexts.md`'s aspirational use-case list but is not one of the "seven" named in this feature's request)? This determines whether the eventual Projects↔Goal relation (Phase C) has a target to attach to, and whether `Project.goalId` will ever be exercised in the Notion view.
