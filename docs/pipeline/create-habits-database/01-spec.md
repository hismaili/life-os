# 01 — Specification: Create Habits Database

Status: Draft for Architect review
Owner (Specifier stage): pipeline automation
Source input: feature request "Create Habits Database" + `CLAUDE.md`; `docs/architecture/03-Domain-Model.md`; `docs/architecture/04-Bounded-Contexts.md` (use-case catalogue: Projects, Tasks, Knowledge, Habits, Journal, Resources, People); `docs/architecture/05-Ubiquitous-Language.md` ("Habit — Recurring actions and routines," Atomic Habits context); the completed **Create Tasks Database** branch (`docs/pipeline/create-tasks-database/01-spec.md`, `02-architecture.md`, ADR-0009) and **Create Projects Database** branch (`docs/pipeline/create-projects-database/01-spec.md`, ADR-0005..0008), whose pattern this spec mirrors and binds to; and existing code under `backend/src/main/java/com/lifeos/{domain/{habit,workspace},application/{usecase/habit,port,dto/workspace},infrastructure/adapter/notion}`.

> This spec covers **one Phase-B provisioning step**: the creation/verification/repair of the **Habits** database as a child of the already-provisioned Dashboard page. It is the **fourth of the seven Phase-B database steps** (`ProvisionedResourceType.HABITS_DB` — `domain/workspace/ProvisionedResourceType.java` line 5); Projects, Tasks, and Knowledge are done and green, Habits reuses the exact idempotent pattern those three established. As with Tasks (and unlike Projects), **no domain-model change is a prerequisite here**: `Habit` (`domain/habit/Habit.java`) and `Frequency` (`domain/habit/Frequency.java`) already exist, complete and self-validating, with every field this step's schema needs. `CreateHabitsDatabaseService` (`application/usecase/habit/CreateHabitsDatabaseService.java` line 20) is currently a stub (`UnsupportedOperationException`); the generic database slice of `NotionProvisioningAdapter`/`NotionProvisioningPort` (`createDatabase`, `verify`, `findChildByIdentity`, `repairShape`) is already implemented and proven by the Projects, Tasks, and Knowledge steps. This spec does not re-specify the orchestrator (`CreateWorkspaceUseCase`), the Dashboard step, the other three completed database steps, the other three not-yet-specified database steps, relations/rollups/formulas, or sample data — those are separate, already-specified-or-future collaborators. Where this spec repeats a decision already made by Create Dashboard's, Create Projects Database's, or Create Tasks Database's architecture (strict idempotency, verify-before-trust, per-step ledger transaction, single process-level token, fail-loudly on `>1` identity match, name-only shape verification), it does so only to bind this step to that contract, not to re-litigate it.

## 1. Summary

"Create Habits Database" is a Phase-B provisioning step invoked by the Create Workspace orchestrator once Phase A (Create Dashboard) succeeds: given an existing `Workspace` aggregate and its confirmed Dashboard page id, it provisions (or, on re-run, verifies and reconciles) a single Notion database — **Habits** — as a child of the Dashboard, with the structural property schema needed to represent the `Habit` aggregate. The user value: every workspace gets one stable, non-duplicated Habits database, created once, whose schema is verified and repaired on every re-run rather than drifting silently — the fourth of the seven container databases the eventual Create Relations phase will link together (a future Habits→Areas relation, per `Habit.areaId`). Today `CreateHabitsDatabaseService.execute` throws `UnsupportedOperationException` (`CreateHabitsDatabaseService.java` line 20); the generic database slice of `NotionProvisioningAdapter` is already implemented and proven by the Projects/Tasks/Knowledge steps. This spec defines what "implemented" must mean for the Habits step specifically — a service supplying a Habits-specific `DatabaseSpec`/`ExpectedShape` to that existing adapter, with **no adapter change and no domain-model change** required.

## 2. Actors & stakeholders

- **Primary user (Person aggregate)** — indirectly benefits; does not invoke this step directly. Invokes "Create Workspace," which invokes this step as part of Phase B.
- **`CreateWorkspaceUseCase` / `CreateWorkspaceService` (orchestrator)** — the sole caller of `CreateHabitsDatabaseUseCase.execute(workspaceId)`, already wired and expecting a `ProvisioningStepResult` of type `ProvisionedResourceType.HABITS_DB`. Runs this step only if Phase A (Dashboard) succeeded; treats this step's result as one of seven inputs to `phaseBOk`, which gates Phase C (Relations). Runs independently of, not after, the Projects/Tasks/Knowledge steps — sibling Phase-B steps with no ordering dependency between them.
- **`CreateHabitsDatabaseService` (this step's application service)** — currently a stub (`CreateHabitsDatabaseService.java`); owns the step's idempotent verify/create/repair/adopt/record sequence for the `HABITS_DB` resource. Depends on `NotionProvisioningPort` and `WorkspaceLedgerWriter` — the same collaborator set `CreateTasksDatabaseService`/`CreateProjectsDatabaseService` already use.
- **`NotionProvisioningPort` / `NotionProvisioningAdapter` (infrastructure)** — driven port/adapter; its database-oriented members (`createDatabase`, `verify`, `findChildByIdentity`, `repairShape`) are already implemented and exercised by the Projects/Tasks/Knowledge steps. This step supplies a Habits-specific `DatabaseSpec`/`ExpectedShape` argument; it introduces no new port method and no adapter-level change.
- **`WorkspaceLedgerWriter`** — the shared, already-implemented collaborator (`record(workspaceId, HABITS_DB, notionId)`) that performs this step's ledger write in its own `@Transactional` unit. This spec does not change its contract.
- **Downstream pipeline roles (Architect, SME, Implementer, QA, Auditor)** — consumers of this spec; because the Tasks step already re-proved the pattern with a `select`-from-enum property (ADR-0009), this branch is expected to be a low-novelty, pattern-application pass, not a new-design pass.

## 3. Functional requirements

- **FR-1**: The system shall accept a request to provision the Habits database for an existing `Workspace`, identified by `workspaceId` (`UUID`), matching the existing `CreateHabitsDatabaseUseCase.execute(UUID workspaceId)` contract (`CreateHabitsDatabaseUseCase.java`). No other input is required — the database's title, parent page, and property schema are derived from the `Workspace` aggregate and this step's own fixed schema definition (§3, property table), not supplied by the caller.
- **FR-2**: Given a `workspaceId` that does not correspond to any persisted `Workspace`, the system shall fail explicitly (not silently no-op), surfacing an error the orchestrator converts into a `FAILED` `ProvisioningStepResult` (mirrors Create Tasks/Projects Database FR-2 and `WorkspaceLedgerWriter`'s existing "Workspace not found" convention).
- **FR-3**: Given a `workspaceId` whose `Workspace` has no confirmed `DASHBOARD` ledger entry, the system shall fail explicitly rather than attempt to create a database with no known parent page — this step's precondition is a live, verified Dashboard id (in practice already enforced by the orchestrator's `runOrBlock(phaseAOk, …)`, but this step must not silently proceed if invoked directly with that precondition unmet).
- **FR-4**: On a valid request where the Workspace's provisioning ledger has **no** `HABITS_DB` entry, and live verification against Notion (scoped to children of the confirmed Dashboard page) finds no matching database, the system shall create exactly one new Notion database as a child of the Dashboard page, titled **"Habits"** (a deterministic identity marker, mirroring the Projects/Tasks steps' fixed title constants), with the property schema defined in §3's property table, and record it in the ledger with its Notion database id. Outcome: `CREATED`.
- **FR-5**: On a valid request where the ledger has a `HABITS_DB` entry **and** live verification confirms the referenced Notion database still exists and matches the expected shape (title + the full required-property set of §3, name-only per ADR-0008), the system shall make no write calls to Notion and shall report outcome `RECONCILED`.
- **FR-6**: On a valid request where the ledger has a `HABITS_DB` entry but live verification finds the referenced Notion database **missing** (deleted out-of-band) or **present but drifted** (renamed, or missing one or more required properties from §3), the system shall repair it — re-creating the database if deleted, or correcting the drifted shape (renaming and/or adding the missing properties) if present-but-wrong — and shall update the ledger entry with the (possibly new) Notion database id. Outcome: `REPAIRED`.
- **FR-7**: Before trusting any ledger-recorded Habits-database id, the system shall verify it live against Notion (existence + expected shape) rather than assuming the ledger is accurate — the ledger is a hint, live Notion is the source of truth (mirrors Create Tasks/Projects Database FR-7; inherits Create Workspace's strict-idempotency contract).
- **FR-8**: If no ledger entry exists but a database matching the expected Habits-database identity (deterministic identity: a database directly parented under the confirmed Dashboard page carrying the expected title marker, verified through `NotionProvisioningPort.findChildByIdentity(dashboardId, HABITS_DB, expected)`) is found live in Notion, the system shall adopt that database's id into the ledger rather than creating a duplicate — closing the create-succeeded-but-ledger-write-failed race window (mirrors Create Tasks/Projects Database FR-8).
- **FR-9**: Where identity resolution (FR-8, or the drift check in FR-6) finds **more than one** database under the Dashboard matching the Habits identity, the system shall fail loudly (not adopt or repair an arbitrary match) — mirrors Create Tasks/Projects Database's / Create Dashboard's `>1` match → `FAILED` rule.
- **FR-10**: The system shall record the confirmed Notion database id (whether newly created, reconciled, or repaired) into the Workspace provisioning ledger via the existing `WorkspaceLedgerWriter.record(workspaceId, HABITS_DB, notionId)` collaborator, in that collaborator's own short transaction — this step does not introduce a new transactional write path.
- **FR-11**: The system shall return a `ProvisioningStepResult(HABITS_DB, outcome, detail)` reflecting exactly one of `CREATED`, `RECONCILED`, `REPAIRED`, or a propagated failure for every invocation — never `void`, never a swallowed exception (matches the existing interface signature, `ProvisioningStepResult`'s compact-constructor contract, and `CLAUDE.md` "no silent no-op").
- **FR-12**: When Notion API calls made by this step fail (network error, rate limit, authentication/token failure, unexpected response shape), the system shall not partially update the ledger — either the full verify-and-write sequence for this step succeeds and the ledger reflects the confirmed state, or it fails and the ledger is left exactly as it was before this invocation. The failure shall propagate as an exception for the orchestrator to convert to a `FAILED` result (FR-11), not be swallowed inside this step.
- **FR-13**: Re-running this step any number of times for the same `workspaceId` with no out-of-band changes to Notion shall converge to the same single Habits database (same Notion id) and never create a second database — the idempotency contract this spec exists to bind (`CLAUDE.md`; Create Tasks/Projects Database FR-13).
- **FR-14**: This step shall create/verify/repair **only** the Habits database's own structural shape (title + the property schema of §3) — it shall not create, populate, or verify any relation, rollup, formula, database row, or sample record, and it shall not touch any other provisioned resource (`DASHBOARD`, `PROJECTS_DB`, `TASKS_DB`, `KNOWLEDGE_DB`, or any other `*_DB` type). The `Habit.areaId` link (a Notion "relation" property pointing at a future Areas database) is explicitly excluded from this step's created shape — see §8.
- **FR-15**: The `Frequency` `select` property's seeded option set shall equal, one option per enum constant, `Frequency.values()` (`{DAILY, WEEKLY, MONTHLY}`) — no more, no fewer options, and no option not backed by an enum constant, mirroring the Status-as-`select` precedent (ADR-0006, ADR-0009) applied to `Frequency`.

### Property schema this step must create (title property + minimum required properties)

| Property | Notion type | Grounding | Notes |
|---|---|---|---|
| **Name** (database title property) | `title` | `Habit.name` — `backend/src/main/java/com/lifeos/domain/habit/Habit.java` line 12; enforced non-blank by `Habit.create` | Required at creation; the database's Notion title property. |
| **Frequency** | `select` | `Habit.frequency` (`Frequency`) — `Habit.java` line 13; `Frequency` — `domain/habit/Frequency.java`, a closed enum `{DAILY, WEEKLY, MONTHLY}` | Options seeded from `Frequency.values()`, one per enum constant, following the `select`-not-Notion's-native-`status`-type decision already made and reasoned for Projects/Tasks (`docs/pipeline/create-projects-database/adr/ADR-0006-property-type-mapping-status-as-select.md`) and the label-source precedent set for Tasks (`docs/pipeline/create-tasks-database/adr/ADR-0009-taskstatus-select-option-labels.md`): a `select` is fully API-manageable (create/add/repair with no UI-only step), which strict idempotency (NFR-1) requires. `Frequency`, like `TaskStatus`, has no `displayName()` — mapping enum constant names to option labels (verbatim, e.g. `"DAILY"`, or humanized, e.g. `"Daily"`) is a presentation-formatting decision left to the Architect/SME, not fixed by this spec (`[ASSUMPTION]`; does not affect any FR/AC since verification is name-only per ADR-0008 and the enum itself is unchanged). |

**No Description property and no date property are created by this step.** Unlike `Task` (`description`, `dueDate`) and `Project`, `Habit` has neither a description field nor any date field (`domain/habit/Habit.java` fields: `id`, `name`, `frequency`, `workspaceId`, `areaId` — verified by direct inspection of the current source). The schema this step creates is therefore intentionally minimal — two properties only — and must not be padded with a Description or Due Date property by analogy to Tasks; doing so would create a Notion property with no backing domain field, contradicting `CLAUDE.md`'s "no primitive obsession"/schema-follows-domain discipline this pipeline enforces.

Excluded from this step's created shape (see §8 for the full boundary): the **Area** link. `Habit.areaId` (`Habit.java` line 15) implies a Habit belongs to (or is scoped by) an Area at the domain level, but a Notion "relation" property requires the *target* database to already exist — an Areas database is not among the four already-completed Phase-B steps and its own provisioning step is not specified here; the relation itself is in any case deferred to the "Create Relations" phase (Phase C), per the project-wide decision already recorded for the analogous Tasks↔Projects and Projects↔Area/Goal links (`docs/pipeline/create-tasks-database/01-spec.md` §8; `docs/pipeline/create-projects-database/01-spec.md` §8, "OQ-B"). `Habit.workspaceId` (`Habit.java` line 14) is not a Notion-surfaced property — the Habits database's membership in a workspace is expressed structurally (as a child of that workspace's Dashboard page), exactly as for the Tasks and Projects databases.

## 4. Acceptance criteria (Given/When/Then)

**FR-1 — input contract**
- Given a valid `workspaceId` for an existing `Workspace` with a confirmed Dashboard, when `CreateHabitsDatabaseUseCase.execute(workspaceId)` is called, then the step runs without requiring any additional caller-supplied parameter.

**FR-2 — workspace not found**
- Given a `workspaceId` with no corresponding persisted `Workspace`, when the step executes, then it throws (e.g. `IllegalStateException`, matching `WorkspaceLedgerWriter`'s and `CreateTasksDatabaseService`'s existing convention) and makes no Notion API call.

**FR-3 — missing Dashboard precondition**
- Given a `Workspace` whose ledger has no confirmed `DASHBOARD` entry, when the step executes, then it fails explicitly (throws, or is never reached because the orchestrator's `runOrBlock` already returned `BLOCKED`) rather than attempting a Notion call with an unknown parent page id.

**FR-4 — first-time creation**
- Given a `Workspace` whose ledger has no `HABITS_DB` entry and Notion has no matching database under the confirmed Dashboard, when the step executes, then exactly one new Notion database titled "Habits" is created as a child of the Dashboard with the full property schema of §3 (Name, Frequency), the ledger gains a `HABITS_DB` entry with that database's id, and the returned `ProvisioningStepResult` has `outcome = CREATED`.

**FR-5 — pure reconcile (idempotent re-run, no drift)**
- Given a `Workspace` whose ledger has a `HABITS_DB` entry and live Notion verification confirms that database exists with the expected title and the full required-property set, when the step executes, then no Notion write call is made, the ledger is left unchanged, and the returned result has `outcome = RECONCILED`.

**FR-6a — repair after out-of-band deletion**
- Given a `Workspace` whose ledger has a `HABITS_DB` entry but the referenced Notion database no longer exists, when the step executes, then a new Habits database is created (or, per FR-8, an orphan matching identity is adopted first), the ledger's `HABITS_DB` entry is updated to the resulting id, and the returned result has `outcome = REPAIRED`.

**FR-6b — repair after out-of-band drift (rename or missing property)**
- Given a `Workspace` whose ledger has a `HABITS_DB` entry and the referenced Notion database still exists but has been renamed or is missing the Name or Frequency property from §3, when the step executes, then the database's shape is corrected in place (same Notion id retained; missing properties added, title corrected), the ledger entry is confirmed/updated, and the returned result has `outcome = REPAIRED`.

**FR-7 — verify-before-trust**
- Given a `Workspace` whose ledger has a `HABITS_DB` entry, when the step executes, then it calls Notion to verify that entry's live existence and full property shape before returning `RECONCILED` — it never returns `RECONCILED` purely because a ledger row is present.

**FR-8 — orphan adoption (race recovery)**
- Given a `Workspace` whose ledger has no `HABITS_DB` entry, but a database matching the expected Habits identity already exists live in Notion as a child of the Dashboard (e.g. a prior run created it but crashed before the ledger write), when the step executes, then the existing database is adopted (its id recorded in the ledger) rather than a second database being created, and the returned result reflects `RECONCILED` (if matching) or `REPAIRED`/`CREATED` per the same orphan-verify branching the Tasks/Projects steps already implement — never a second, duplicate `CREATED` database.

**FR-9 — fail loudly on ambiguous identity**
- Given more than one database under the Dashboard matches the expected Habits identity (title marker), when the step executes its identity lookup, then it does not adopt or repair any of them; it fails, and the returned/propagated result is `FAILED` with a non-blank `detail` explaining the ambiguity.

**FR-10 — ledger write path**
- Given any of the FR-4/FR-5/FR-6/FR-8 scenarios reach a confirmed Notion database id, when the step completes, then the ledger update is performed through `WorkspaceLedgerWriter.record(workspaceId, HABITS_DB, notionId)` and that write is durably committed in its own transaction, independent of the orchestrator's transaction boundary.

**FR-11 — result contract**
- Given any successful execution path, when the step returns, then the result's `type` is `HABITS_DB` and `outcome` is exactly one of `CREATED`/`RECONCILED`/`REPAIRED`.
- Given any failure path, when the step raises an exception, then no `ProvisioningStepResult` is fabricated by this step itself — the exception propagates for the orchestrator's `runOrBlock`/`runStep` to convert into `FAILED` with a non-blank `detail`.

**FR-12 — no partial ledger write on external failure**
- Given a Notion API call within this step fails (timeout, 5xx, rate limit, 401/403), when the step executes, then the ledger is not modified, and the thrown exception surfaces to the caller unmodified in essence.
- Given the Notion API call succeeds but the subsequent `WorkspaceLedgerWriter.record` call fails, when the step executes, then the created/repaired Notion database is left in place (Notion has no transactional rollback), and the next run's FR-8 orphan-adoption path is responsible for reconciling the ledger to the already-existing database.

**FR-13 — idempotent convergence**
- Given the step is run three times consecutively with the same `workspaceId` and no out-of-band Notion changes between runs, when each run completes, then exactly one Habits database exists in Notion across all three runs, and the ledger's `HABITS_DB` entry references that same database id after every run.

**FR-14 — scope boundary**
- Given the step completes successfully, when its `NotionProvisioningPort` call log/interactions are inspected, then no `ensureRelation`, `ensureRollup`, `ensureFormula`, `insertSampleRecords`, or any other database type's `createDatabase`/`verify`/`repairShape` call is invoked by this step, and no `DASHBOARD`, `PROJECTS_DB`, `TASKS_DB`, `KNOWLEDGE_DB`, or other `*_DB` ledger entry is written by this step (the `DASHBOARD` entry is only read, per FR-3).
- Given the created or verified Habits database's schema is inspected, when compared against §3's property table, then it contains exactly two properties (Name, Frequency), no Description or date-typed property, and no relation-typed property pointing at any other LifeOS database.

**FR-15 — Frequency option-set fidelity**
- Given the Habits database is created (FR-4) or repaired with a missing Frequency property (FR-6b), when the resulting Frequency `select` property's option set is inspected, then it contains exactly three options, one per `Frequency.values()` constant (`DAILY`, `WEEKLY`, `MONTHLY`), and no option that does not correspond to a current enum constant.

## 5. Non-functional requirements

- **NFR-1 (Strict idempotency)**: This step must be safely re-runnable any number of times per FR-13, consulting live Notion (not just the ledger) as the source of truth — inherits Create Dashboard's, Create Projects Database's, and Create Tasks Database's idempotency contract; this spec does not weaken it for the Habits database specifically.
- **NFR-2 (Resilience to external failures)**: A Notion API failure during this step must leave both the ledger and any already-created Notion database in a state the *next* run can reconcile without manual cleanup (FR-12); no compensating transaction/rollback of the Notion side is required or expected.
- **NFR-3 (Testability)**: `CreateHabitsDatabaseService`'s verify/create/repair/adopt/record sequencing logic must be unit-testable against a mocked `NotionProvisioningPort` and `WorkspaceLedgerWriter`, with zero real Notion calls.
- **NFR-4 (No silent no-op)**: Until this service genuinely implements the verify/create/repair/adopt/record sequence for the Habits resource, `CreateHabitsDatabaseService.execute` must continue to fail explicitly (`UnsupportedOperationException` or equivalent) rather than appear to succeed.
- **NFR-5 (Observability)**: Each invocation's outcome (`CREATED`/`RECONCILED`/`REPAIRED`/failure) must be logged with enough detail (workspaceId, Notion database id, prior ledger state) to debug a multi-run reconciliation history — feeds the orchestrator's `ProvisioningReport`.
- **NFR-6 (Security / no token leakage)**: This step uses the single process-level Notion integration token already decided for v0; it introduces no new secret or token-scoping requirement. The token must never appear in logs or the `detail` field of a `ProvisioningStepResult` or in any propagated exception message.
- **NFR-7 (Failure isolation)**: A failure in this step (FR-11/FR-12) must not corrupt or partially mutate any other provisioned resource's ledger entry (`DASHBOARD`, `PROJECTS_DB`, `TASKS_DB`, `KNOWLEDGE_DB`, or any other `*_DB` type) — the orchestrator's existing `runOrBlock` per-step isolation already provides this at the orchestration level; this step must not introduce any shared mutable state or side effect that breaks that isolation. In particular, a Habits-step failure must leave the Projects/Tasks/Knowledge steps (and vice versa) free to still run and succeed independently, per the orchestrator's existing `phaseBOk` aggregation, which only gates Phase C, not the sibling Phase-B steps themselves.
- **NFR-8 (Ledger recording)**: Every successful terminal outcome (`CREATED`/`RECONCILED`/`REPAIRED`) must result in exactly one `PROVISIONED_RESOURCE` ledger entry of type `HABITS_DB` reflecting the confirmed Notion id — never zero (a successful-looking result with no ledger record) and never more than one (a duplicate/stale entry for the same type), consistent with `Workspace.record`'s upsert-by-type semantics.
- **NFR-9 (Performance)**: `[ASSUMPTION — carried from Create Tasks/Projects Database NFR-9]` No hard latency SLA; a single successful run should require at most a small, bounded number of Notion API calls (one verify/search + at most one create-or-repair + one ledger write) — no polling loops or unbounded retries within a single invocation.
- **NFR-10 (Rate-limit awareness)**: `[ASSUMPTION — carried from Create Dashboard NFR-8 / Create Tasks/Projects Database NFR-10]` Notion's documented rate limit applies; this step's implementation must not assume unlimited throughput, though the specific backoff strategy is an Architect/Implementer decision, not fixed here.

## 6. Data & entities (conceptual only)

- **Workspace**: existing aggregate root that owns the provisioning ledger this step reads from and writes to, and whose confirmed `DASHBOARD` ledger entry supplies this step's required parent-page id. Referenced here only by its `id` (UUID).
- **Habit**: existing, complete domain aggregate (`domain/habit/Habit.java`) this database represents — `name`, `frequency` (`Frequency`), `workspaceId`, `areaId`. This step provisions the *structural container* (database + property schema) for future `Habit` records; it does not create any row/record. Note: unlike `Task`/`Project`, `Habit` has no `description` and no date field, so the schema this step creates is exactly two properties (§3).
- **Frequency**: existing closed domain enum (`domain/habit/Frequency.java`) — `{DAILY, WEEKLY, MONTHLY}` — the sole source of the Frequency property's seeded `select` options.
- **Habits database**: the single Notion database that is this step's sole subject — a database directly parented under the workspace's Dashboard page, with the property schema of §3. Conceptually: `Workspace 1—0..1 HabitsDatabase` before this step runs, `Workspace 1—1 HabitsDatabase` after a successful run.
- **Provisioned Resource (type = HABITS_DB)**: the existing ledger entry value object (`ProvisionedResourceType.HABITS_DB`, `notionId`, `provisionedAt`) this step is responsible for creating/updating. No new domain type is introduced by this spec.
- **Expected Shape (Habits)**: the conceptual target state this step verifies against — title "Habits" + the required-property-name/type set of §3 (`ExpectedShape(String title, List<PropertyDefinition> requiredProperties)`, `application/port/ExpectedShape.java`).

Relationships: `Habit.areaId` describes a conceptual "a Habit is scoped by an Area" link to the (not-yet-provisioned) `Area` aggregate, but establishing the corresponding Notion relation property is explicitly not this step's concern (§8) — it depends on an Areas database step not yet specified, and is in any case deferred to Phase C (Create Relations).

## 7. Constraints & assumptions

- Constraint: must implement the existing `CreateHabitsDatabaseUseCase.execute(UUID workspaceId) : ProvisioningStepResult` signature and the existing `CreateHabitsDatabaseService` class (currently a stub) without changing the interface shape — the orchestrator (`CreateWorkspaceService`) already depends on this exact contract.
- Constraint: must use the existing `WorkspaceLedgerWriter.record(...)` collaborator for the ledger write; this spec does not reopen the transaction-boundary decision made for Create Dashboard / Create Projects Database / Create Tasks Database.
- Constraint: must use the existing `NotionProvisioningPort` database-oriented contract (`createDatabase(String parentPageId, DatabaseSpec)`, `verify(String databaseId, ProvisionedResourceType type, ExpectedShape)`, `findChildByIdentity(String parentPageId, ProvisionedResourceType type, ExpectedShape)`, `repairShape(String databaseId, ExpectedShape)`) exactly as already defined in `application/port/NotionProvisioningPort.java` and already exercised by `CreateTasksDatabaseService`/`CreateProjectsDatabaseService`. No port change is anticipated or in scope; if this step's needs cannot be met by the existing port shape, that is an Architect-level finding, not a redesign this spec pre-decides.
- Constraint: no `Habit`/`Frequency` domain change — `Habit` already carries every field (`name`, `frequency`) this step's §3 schema needs. This spec must not introduce any change to `domain/habit/`.
- `[ASSUMPTION]` The Habits database's identity for verification/adoption purposes (FR-8) is "a database directly parented under the confirmed Dashboard page carrying the title 'Habits'" — mirrors the Projects/Tasks steps' identity heuristic (title + parent scoping), which is itself a fixed decision now (not re-opened here).
- `[ASSUMPTION]` "Habits" is the exact database title (mirroring the Projects/Tasks steps' fixed `"Projects"`/`"Tasks"` title constants); a different display name (e.g. an emoji-prefixed title) is a downstream Architect/SME styling decision that does not change any FR.
- `[ASSUMPTION]` The Frequency `select` option **labels** (verbatim enum constant name vs. a humanized display string) are a presentation-formatting choice left to the Architect/SME, since `Frequency` — like `TaskStatus` — has no `displayName()` method and this spec does not introduce one (per the "no domain change" constraint above), following the precedent set by ADR-0009 for Tasks. This does not affect any FR/AC: verification is name-only per ADR-0008 (property existence, not option-set equality for repair purposes; FR-15 constrains the option set only at creation time), so the specific label choice cannot cause a spurious drift/repair.
- Constraint: single process-level Notion token (no per-Person token) — inherited unchanged from Create Workspace/Create Dashboard/Create Projects Database/Create Tasks Database.

## 8. Out of scope

- Establishing any Notion relation, rollup, or formula property, including but not limited to a Habits↔Areas relation (backing `Habit.areaId`) — that is the "Create Relations" phase (Phase C), specified separately, and requires both the Habits and (not-yet-specified) Areas databases to already exist.
- Any database property whose Notion type requires another LifeOS-provisioned database to exist first (relation-typed properties in general).
- Populating the Habits database with rows or sample data, and any habit-tracking "check-in"/completion-log concept — that is out of scope for this structural-provisioning step entirely (rows generally belong to the "Populate Example Data" phase, Phase F; per-day habit check-ins are not part of the `Habit` aggregate as it exists today and are not addressed by this spec at all).
- Provisioning any of the other three not-yet-specified databases (Journal, Resources, People) or re-provisioning Projects/Tasks/Knowledge — each gets its own spec; this document only defines the contract for the Habits step.
- The orchestrator's (`CreateWorkspaceService`) sequencing, blocking, and reporting logic — already implemented; this spec only defines the contract this one step must fulfill within that sequence.
- The Create Dashboard step itself, and any change to how the Dashboard's id is confirmed — this step only consumes that confirmed id as a precondition (FR-3).
- Real OAuth / interactive Notion authorization flow — unchanged from Create Dashboard/Create Workspace/Create Projects Database/Create Tasks Database's single pre-provisioned process-level integration token.
- Database view configuration (Notion "views" — board/table/calendar/filters/sorts), icon/cover, or any presentation concern beyond the property schema needed to identify and later relate to this database — a presentation concern for `notion/` assets (per `CLAUDE.md`), not this backend provisioning step.
- Habits database deletion or archival.
- Any change to `NotionProvisioningPort`'s method signatures or value types, or to the `NotionProvisioningAdapter` — this step reuses the existing, already-implemented database slice as-is.
- Any change to `Habit`/`Frequency` domain code — the domain aggregate is already complete for this step's purposes (§7).
- Choosing/adding a `displayName()`-style humanized label for `Frequency` — left as an `[ASSUMPTION]`/downstream styling decision (§7), mirroring the tracked-but-deferred follow-up already recorded for `TaskStatus` in ADR-0009; if desired, that is itself a (small, low-risk) domain-model change outside this spec's authorization.
- Adding a Description property or any date property to the Habits schema — explicitly excluded because `Habit` has neither field (§3); this is a hard boundary, not an `[ASSUMPTION]`.

## 9. Open questions for the stakeholder

None. The schema (§3) is fully grounded in the already-complete `Habit`/`Frequency` domain aggregate (verified directly against current source: `domain/habit/Habit.java`, `domain/habit/Frequency.java`), the identity/idempotency pattern is fixed by the already-implemented Create Projects Database and Create Tasks Database branches, and the property-type mapping (Frequency-as-`select`, sourced from a closed enum with no `displayName()`) follows the already-decided and reasoned precedent of ADR-0006/ADR-0008/ADR-0009 with no new type-mapping question introduced. The only deferred item — the Frequency option label formatting (§7) — is flagged as an `[ASSUMPTION]` because it does not affect any functional requirement or acceptance criterion, not because it requires a stakeholder decision to proceed.
